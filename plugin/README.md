# WordPress Manager

This is a declarative Zoer Integration API v1 plugin. It contains no frontend bundle and is never imported into the backend process. Zoer renders its workspace, runs its declarative workers inside the configured isolated plugin runner, and supplies a host-owned WordPress Sites manager for provider-sensitive operations.

The Sites manager unifies DDEV, WordPress Playground, and connected Hostinger installations. DDEV and Hostinger sites have one-click Preview/Admin controls. DDEV plugin/theme install, activate, deactivate, update, and uninstall operations create an integrity-checked application backup, capture baseline Site Health, apply exact slugs in batches, and restore the backup if the operation fails or adds critical checks. Playground is inventory-only in this manager because it does not expose the dedicated DDEV WP-CLI boundary.

Zoer's host-owned collection lifecycle API lets Hosted API chat list active and archived local WordPress sites, create a durable DDEV site, archive or restore DDEV and Playground sites, and plan removal of an archived DDEV site. Archive is the recoverable default. Final removal requires Full access, a fresh SHA-256 plan fingerprint, and its exact confirmation phrase. It unlists the site from Zoer and the bridge while preserving the DDEV project directory and database files. Installed CLI agents can call the same HTTPS endpoints only in an intentionally passwordless development deployment; authenticated host-tool bridging is not yet live.

Hostinger connections use the official HTTP API rather than shelling out to the CLI. The token is stored as an encrypted Zoer Secret and never returned to the browser after connection. The manager discovers installations, creates official temporary WordPress login links, searches plugins/themes, queues exact extension mutations, shows Hostinger vulnerability data, creates websites, and records provider receipts. Because Hostinger's public shared-hosting API does not expose backup creation, production update/uninstall and replacement plans require a user-confirmed hPanel recovery point created in the preceding 24 hours.

Full-site publishing supports a running, standard-root DDEV source and an existing Hostinger website. Zoer creates a local application backup, freezes and exports a SHA-256-manifested `tar.gz` WordPress root plus uncompressed SQL, uploads both through Hostinger's TUS endpoint, and calls the official destructive WordPress import endpoint. New targets are verified through installation discovery and a public-address-pinned HTTPS smoke check. Because an existing installation can make an asynchronous replacement appear complete prematurely, replacements remain `verification_required` until the user checks hPanel, the public page, Admin, permalinks, and assets. New-target and replacement modes use different typed confirmation phrases. Bedrock/subdirectory sources, database merging for live WooCommerce/membership data, automated Hostinger staging promotion, and remote backup creation are not advertised as live.

The host-rendered workspace also accepts a complete, single-site UpdraftPlus backup set (database, plugins, themes, uploads, and others) and creates a new persistent WordPress Playground computer from it. Files upload in bounded chunks and are size/SHA-256 verified before use. Archive paths, links, member counts, and expanded sizes are checked; incompatible cache/database drop-ins are quarantined. This importer supports the standard `wp_` prefix and does not yet support multisite or split component archives.

The plugin uses the host-owned `runtime-resources` capability to reach only the DDEV connector and only the operations declared per action. It never receives the DDEV bridge URL/token, Docker socket, project path, database password, or database host port.

`sites.refresh` also creates stable, credential-free linked MariaDB records in Zoer's normal Databases view. Schema and read-only queries are delegated back through the DDEV adapter; deleting a registry link does not delete the WordPress project or its database.

DDEV must be configured on the Zoer server with `DDEV_BRIDGE_URL` and `DDEV_BRIDGE_TOKEN`. Preview/Admin navigation is rendered by the host; the plugin never receives a URL credential, password, or WordPress cookie. In protected deployments, Admin auto-login uses a 60-second HttpOnly one-time handoff bound to the issuing Zoer session. Passwordless development mode permits the same one-use, rate-limited handoff without a Zoer session because the entire Zoer API is already intentionally open. The current handoff store assumes one backend replica. Legacy destructive declarative actions are declared `approval: always`, pause in Zoer's durable workflow engine, and resume only after one exact Full access approval; the server recomputes the reviewed plan before execution. The host-owned Sites manager separately uses exact plan fingerprints plus typed production confirmations, because provider tokens and long-running TUS transfers are not delegated to plugin workers.

Application backups include the WordPress database and the resolved `WP_CONTENT_DIR` (including Bedrock-style content paths), with SHA-256 component and manifest verification. Git remains the source of truth for repository/core/vendor files outside that directory.

Fleet inventory refreshes isolate per-site failures and inspect at most eight running sites per run; refresh again after narrowing the active fleet when managing more than eight sites.
